# プロファイル適用までのレスポンスアップ

## 背景 / 目的
Issue #6 の要望は、再生デバイス切替後に保存済みプロファイルが適用されるまでの待ち時間を短縮し、適用前の音量で音が再生される時間をできるだけなくすことです。

現状はデバイス変更イベントごとに 800ms の末尾デバウンスを行ってから、確定したデフォルトデバイスの取得とプロファイル適用を開始しています。この待機時間が、プロファイル適用までの主な遅延要因になっています。

## 変更内容
- `DeviceChangedEventArgs` にデバイス変更通知の種別を追加し、`OnDefaultDeviceChanged` と状態変更・追加・削除通知を区別する。
- `OnDefaultDeviceChanged` の場合は、800msのデバウンスを待たずにプロファイル適用を開始する。
- 短時間に複数発火する Windows のデバイス変更通知に対する800msの末尾デバウンスは、検証・救済パスとして維持する。
- 即時適用と検証パスを直列化し、同一デバイスの3秒間の重複抑制によって二重適用・二重通知を防ぐ。
- デバウンス時間をコンストラクタから注入できる構造にし、即時適用・遅延適用・重複抑制・失敗時救済を単体テストで確認する。

## 設計方針

### ハイブリッド方式を採用した理由

当初検討した「デバウンスを800msから100msへ一律短縮する方式」は、デバイスの静定前に処理する可能性があり、Bluetoothなどで通知が断続する場合に誤ったデバイスへ適用するリスクが残ります。また、100msの待機時間も残るため、安定性とレスポンスの両方を優先する要件には十分ではありません。

そこで、通知の意味に応じて処理を分けます。

- `DefaultDeviceChanged`: デフォルトデバイスの変更通知として、800ms待たずに即時適用を開始する。
- `DeviceStateChanged` / `DeviceAdded` / `DeviceRemoved`: 切替完了を保証しないため、従来どおり末尾デバウンス後に処理する。
- すべての通知で800msの検証パスをスケジュールし、切替途中の通知や即時パスでのデバイス解決失敗時に、確定したデフォルトデバイスへ収束させる。

即時適用と検証パスは `SemaphoreSlim` で直列化します。適用が成功した後にデバイスIDと時刻を記録し、同一デバイスに対する3秒間の抑制で二重適用と二重通知を防ぎます。即時適用が失敗した場合は適用済み状態を記録せず、検証パスで再試行します。

### 期待効果

- 切替通知からプロファイル適用開始までの待機を、従来の800msからデバイス解決・プロファイル読込に必要な時間まで短縮する。
- COMコールバックスレッド上でI/Oや音量適用を実行せず、即時処理はスレッドプールで実行する。
- 既存の800ms検証パスを維持し、通知が一時的または複数回発火する環境でも最終状態を安定させる。

### リスクと対策

- 切替途中に複数のデフォルトデバイス変更通知が発火した場合、一時デバイスへ一度適用する可能性がある。検証パスで最終デフォルトデバイスを再取得し、正しいプロファイルへ収束させる。
- 即時適用と検証適用が重なる可能性がある。適用処理の直列化と同一デバイス抑制で重複を防ぐ。
- デフォルトデバイスの取得に失敗する可能性がある。即時パスではログを記録し、検証パスに処理を委ねる。

## 備考
`OnDefaultDeviceChanged` はデフォルトデバイスの切替を示すため即時適用に利用します。一方、デバイス状態変更などの通知は切替完了を保証しないため従来どおり静定後に処理します。即時パスでデバイス解決に失敗した場合や切替途中だった場合も、800ms後の検証パスで確定したデバイスへ収束させます。
